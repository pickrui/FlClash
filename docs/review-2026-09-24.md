# 2026-09-24 桌面本地控制边界审查

基线 `80954ae9`，包含上轮尚未提交的窗口唤醒修复。本轮范围为单实例唤醒、Windows 窗口显示与静默启动、Helper HTTP 入口、Core 摘要和会话归属、桌面 IPC 帧与队列边界

## 确认问题与修复

- 唤醒端口只要接受 TCP 连接就调用 `show()`；从实际旧处理函数提取的隔离脚本确认空连接即可触发。改为校验完整的版本化请求和本次监听生成的随机凭据，逐字节处理分包，拒绝无数据、错误及过期请求；每个连接限时 1 秒，最多保留 16 个待完成连接
- Helper 只绑定 loopback，但没有检查 HTTP 来源与 Host。隔离路由测试发送带 `Origin`、无 Content-Type 的合法 `/start` 请求，修复前确实终止了已有假 Core；外部 Host 请求 `/logs` 返回 200。现在全部路由先校验原生客户端使用的 Host，拒绝 Origin、Sec-Fetch-Site 和缺失或外部 Host；异常请求在接触 Core 会话前返回 403
- Helper 的 JSON 请求体没有大小上限。启动、停止接口现在要求 Content-Length 且不超过 4 KiB，缺少长度返回 411，超限返回 413，均在 JSON 解析前拒绝

Windows 原生重复启动仍只在手动启动时显示已有窗口。Core 固定路径、SHA256 校验、会话 ID 和 PID 核对、停止归属、Linux Unix socket 对端 UID 验证保持原有行为；HTTP 来源检查不替代本机进程身份认证

Linux 原生客户端使用 `Host: flclash-helper`，Windows 使用 `Host: 127.0.0.1:47890`，两者的既有 JSON 请求均满足新边界。Windows 必过工作流新增真实 TCP 唤醒、窗口显示/隐藏及启动参数测试

旧版纯端口唤醒文件不再发出空连接。Windows 原生重复启动路径仍可唤醒旧实例；Linux 升级后需结束旧进程并启动新版才能使用新唤醒协议
